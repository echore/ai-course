The reasoning loop

03-02

The harness supports every turn of the loop

The model selects a next action. The surrounding software manages the state, execution, and result.

Perceive

Receive the goal, task state, and previous results.

→

Reason

Choose a useful next action from the available context.

→

Act

Execute an allowed tool request or generate an output.

→

Observe

Return the result and update the state for the next turn.

Define when the loop stops, what happens when a step fails, and the budget for a realistic task.

Harness responsibilities

03-02

A functional loop needs an operating design

Tools, memory & context

  • Tools interact with external systems.
  • Memory carries information within and across sessions.
  • Context management selects what each model call receives.

Controls, traces & review

  • Guardrails constrain actions and outputs.
  • Observability records execution and failures.
  • AI review checks outputs against explicit criteria.

Human escalation

An operational workflow designed alongside the harness.

  • Names the reviewer and the review package.
  • Defines how the system waits and records the decision.
The FDE scopes these pieces together, validates them during the pilot, and documents ownership at handoff.

Tool scope

03-02

Choose tools by capability and consequences

Tools are functions the agent can request to retrieve information, change records, or run processes.

Read tools

Query an order database, retrieve documents, or inspect tracking.

They do not change external state, but still need appropriate data access.

Write tools

Update a record, send a notification, or trigger a workflow.

Errors can affect customers; define approvals and protection against duplicate changes.

Execution tools

Run a script or start a compute job.

Constrain the environment and resources. The impact depends on the capabilities granted.

Scope the minimum tool set that solves the task; a read-only workflow does not need write access.

Tool execution

03-02

Tool calls need clear contracts and coordination

Model request

Select a tool and supply arguments.

→

Harness execution

Validate inputs and permissions, then call the external function.

→

Result or error

Return a structured observation to the next model call.

A clear tool contract

  • Name the purpose, required arguments, and expected result.
  • Return useful errors; define timeouts and retry behavior.
  • Record whether an external change actually completed.

Dependencies determine order

  • An order lookup may supply the tracking ID for the next call.
  • Independent read tasks may run in parallel.
  • Combine results before making decisions that depend on them.
A request to call a tool is different from confirmation that the tool succeeded.

Memory architecture

03-02

Memory requirements come from session continuity

Short-term memory

The information available during the current session: the goal, previous observations, and running task state.

  • Directly available when included in the model’s context.
  • Bounded by the context window and context-management decisions.

Long-term memory

Persistent storage that can be retrieved across sessions, such as a structured database or a semantic search store.

  • Supports prior interactions, accumulated findings, and task resumption.
  • Stored information must be retrieved into context before the model can use it.
Discovery question: must the agent remember last week’s conversation or resume an unfinished task?

Context management

03-02

Context is assembled for each model call

The context window is finite. The harness selects the goal, instructions, observations, records, and task state needed now.

Step summarization

Compress earlier steps while preserving outcomes, constraints, and unresolved work.

Selective retrieval

Store detailed results externally and retrieve only what is relevant to the current decision.

Running state

Maintain a structured view of progress, completed actions, evidence, and remaining tasks.

Test realistic session lengths. Excess context can fail requests or lose critical information through truncation or poor summarization.

Worked example

03-02

A support case connects tools, memory, and context

Start the investigation

Read the order and fetch tracking using its ID.

→

Continue the session

Record the carrier exception and the checks already completed.

→

Resume tomorrow

Retrieve the case state and verify fresh tracking before proceeding.

Retain what matters

  • Goal, case identifier, verified observations, and remaining questions.
  • Which actions completed and whether anything changed.

Keep context current

  • Retrieve the relevant case rather than every previous conversation.
  • Summarize large results without discarding key evidence.
The next decision should use the right case state and current evidence.

Four types of constraints

03-02

Guardrails define runtime boundaries

Scope limits

Allow only the tools and actions required for the agreed function. A research task should not gain an unrelated write capability.

Budget ceilings

Bound tokens, cost, iterations, and elapsed time. Specify what happens when a limit is reached.

Output checks

Validate required format, disallowed content, sensitive fields, and evidence before delivery. Flag or route failures.

Permission controls

Limit which records and systems the workflow can read or modify, using enforced access controls.

Define the configuration during scoping; verify it during the pilot and document how it can be changed.

Six trace dimensions

03-02

Observability makes execution reconstructable

A wrong final answer may originate several steps earlier. Record enough evidence to find where the behavior diverged.

Actions and information

  • Tool requests, results, errors, and retries.
  • Model inputs and outputs or controlled references to them.
  • Memory reads and writes, including retrieved case state.

Operations and decisions

  • Token use and cost per step and session.
  • Timeouts, error states, and recovery behavior.
  • Review decisions and validated confidence signals, where available.
Use readable session and step IDs. Protect sensitive trace data; record observable execution rather than requiring hidden model reasoning.

Failure diagnosis

03-02

Trace the cause before changing the model

Step 1 · Lookup

Tracking times out; the trace records the error.

→

Step 2 · State update

The harness incorrectly records “delivered” despite missing evidence.

→

Step 3 · Final answer

The model tells the customer the parcel was delivered.

Locate the divergence

Compare the external result, stored state, and context supplied to the next model call.

Fix and re-evaluate

Correct error-to-state handling, then rerun the timeout case and similar failures.

Handoff test: can the receiving team explain this failure from the session trace?

Review before delivery

03-02

AI review adds a bounded quality check

Generate

Produce the proposed output.

→

Review

Check explicit criteria and return useful feedback.

→

Pass or revise

Deliver a pass; revise a failure within the retry budget.

→

Escalate

Send unresolved failures to a human owner.

Define verifiable criteria

  • Required fields and format.
  • Evidence for important claims.
  • Completion of required workflow steps.

Account for the overhead

  • Measure added tokens, cost, and latency.
  • Set a regeneration limit.
  • Keep unresolved cases out of automatic delivery.
Use AI review where it helps measured quality; retain human escalation for unresolved cases.

Review approaches

03-02

Self-reflection and a critic have different roles

Self-reflection

Ask the generating agent to check its own output against named criteria.

  • Can catch omissions and format problems.
  • May repeat the assumptions that caused the original error.

Critic model or prompt

Use a separate review call or model to evaluate the proposed output and evidence.

  • Return acceptance, specific revision feedback, or escalation.
  • A separate call can still share blind spots; validate its judgments.
Review signals must be evaluated on real cases. A model’s stated confidence is not automatically a calibrated probability.

Four decisions to document

03-02

Human escalation needs a working operating path

Who receives the case

Name a role or team with responsibility for reviewing the output or proposed action.

What accompanies it

Include the original request, relevant records, execution evidence, and the trigger for review.

How the decision is recorded

Log the reviewer’s decision and resulting action so recurring failures can inform improvements.

What happens while waiting

Pause the task, return an agreed fallback, or use an existing manual process. Define timeout ownership.

Trigger escalation for unresolved errors, failed review, consequential actions requiring approval, or validated uncertainty signals.

Validation and calibration

03-02

Pilot the harness under realistic conditions

Runtime behavior

  • Use realistic session lengths and document volumes.
  • Test long-term recall and task resumption.
  • Inject timeouts, missing results, and repeated-action cases.

Control and review

  • Test permissions, scope limits, and budget stops.
  • Evaluate output checks and critic decisions.
  • Calibrate any thresholds using real outcomes.

Customer operations

  • Have the receiving team interpret a failed-run trace.
  • Test the escalation queue and waiting behavior.
  • Measure review burden, end-to-end latency, and total cost.
Overly strict thresholds overload reviewers; overly loose thresholds can allow unacceptable cases through.

FDE delivery

03-02

Carry the design through scope, pilot, and handoff

Scope the agreement

  • Tool set and permitted actions.
  • Memory and session-continuity requirements.
  • Context strategy, limits, review criteria, and escalation owner.

Validate during the pilot

  • Representative runs and failure cases.
  • Measured review quality, latency, cost, and operational burden.
  • Verified recovery and human intervention.

Hand off the operating package

  • Configuration and access boundaries.
  • Readable trace examples and recovery runbooks.
  • Named owners and guidance for changing controls and thresholds.
The customer should know how to investigate, intervene, and retest the system as it evolves.
