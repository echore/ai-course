Decomposing
& Designing RAG

Turn a bank’s knowledge-search problem into a private, permission-aware retrieval and generation system.

Module 03-01 · AI Forward Deployed Engineer

The case study

03-01

One bank, three different information needs

Around 4,000 employees across New York, London, and Hong Kong need accurate answers from internal documents.

Research analysts

Spend 2–3 hours locating prior research, comparable filings, and sector memos before writing a note.

Need useful synthesis with verifiable sources.

Compliance officers

Manually search policies and regulatory guidance to answer business questions.

Need precise references and complete coverage.

Senior advisors

Spend half a day locating deal precedents and internal models for a pitch book.

Need relevant prior transactions and source material.

The ask is broad: plain-language questions and accurate answers. Discovery must make “accurate” measurable.

Hard requirements

03-01

Three constraints determine the available design

Private processing

  • Documents, chunks, queries, and model processing stay inside the bank’s approved private environment.
  • No external embedding, generation, or reranking service receives this data.

Existing permissions

  • An answer must not expose information from documents the requester cannot access.
  • Apply this rule across SharePoint, email, and the file server.

Heterogeneous sources

  • SharePoint research, policies, and deal memos.
  • Eight years of Bloomberg and Outlook threads.
  • File-server PDFs, transcripts, and scanned material.
Confirm source hosting and approved connectivity: a cloud connector must not silently violate the private-boundary requirement.

Discovery

03-01

Clarifying questions turn the ask into a scope

Users & workflows

  • Do query patterns differ by role?
  • Cited summary, excerpt, or ranked documents?
  • What workarounds and peak-use periods exist?

Documents & sources

  • What volume, formats, and scan quality?
  • How are threads, attachments, and duplicates handled?
  • What changes and how often?

Infrastructure & permissions

  • What hosting, compute, and model approval are available?
  • Which permissions are direct or inherited?
  • How quickly must access changes take effect?

Success & measurement

  • What counts as a correct, complete answer for each group?
  • Who supplies reference answers and reviews results?
  • What latency and business outcome define success?
Ask before building: the answers change connectors, retrieval behavior, access enforcement, and the evaluation set.

Engineering boundaries

03-01

Decompose the work into seven subproblems

Prepare searchable knowledge

  • 1 · Ingestion: connect all three sources.
  • 2 · Parsing: extract usable text and structure.
  • 3 · Embedding & indexing: store chunk vectors and metadata.

Serve and validate answers

  • 4 · Retrieval: find evidence for the question.
  • 5 · Access enforcement: restrict every candidate to authorized content.
  • 6 · Generation: answer from selected evidence and cite it.
  • 7 · Evaluation: measure retrieval and answer quality by user group.
Each subproblem needs defined inputs, outputs, ownership, and failure handling.

From request to architecture

03-01

Why RAG fits the refined problem

Build private question answering over three document sources, limited to the requester’s authorized evidence and evaluated against role-specific quality criteria.

Retrieve relevant evidence

The corpus is too large to send in full. Retrieve useful sections at query time rather than relying on model memory.

Document updates can be indexed without retraining the generation model.

Generate a grounded response

Supply the question and selected chunks to a self-hosted language model.

Return citations and an explicit limitation when the evidence is insufficient.

RAG supplies evidence to the model; it does not guarantee that the model’s answer is correct.

Architecture overview

03-01

Two pipelines share one searchable corpus

Every stage runs within the approved private environment. Ingestion is scheduled; answering happens at request time.

Connect sources

Read documents, versions, and permissions.

→

Parse & chunk

Preserve structure, source references, and ACLs.

→

Embed

Convert chunk text into vectors locally.

→

Index

Store vectors, text, metadata, and permissions.

Authenticate

Resolve the requesting user and effective access.

→

Retrieve

Embed the query and search only authorized content.

→

Rank & select

Fuse results, optionally rerank, and fit the context budget.

→

Generate

Return a cited answer or state that evidence is insufficient.

Shared components: a compatible embedding configuration and the searchable index. ACL means access control list.

Document ingestion

03-01

Connectors must read content and access metadata

SharePoint

  • Fetch files and source identifiers through an approved API path.
  • Resolve effective permissions separately; do not assume a file response includes them.
  • Capture document versions and modification times.

Email archive

  • Reconstruct message order and remove repeated reply chains.
  • Extract attachments and link them to their thread.
  • Map the archive’s actual permission model.

File server

  • Crawl new or changed files on a source-appropriate schedule.
  • Flag scanned PDFs for OCR.
  • Resolve effective folder and file permissions.
Use a processing queue. Track updates, deletions, duplicate content, and permissions without merging away access boundaries.

Preprocessing

03-01

Parsing prepares evidence, not just raw text

Word & Excel

Extract text, headings, and table structure. Retain useful relationships between labels and values.

Text PDFs

Extract the existing text layer and clean layout artifacts without discarding meaningful sections.

Scanned PDFs

Run local optical character recognition, or OCR. Check recognition quality before indexing.

Email threads

Clean quoted replies, preserve message context, and process attachments as linked documents.

Carry source, document ID, type, version, location, and effective permissions into every downstream chunk.

Deal memosSemantic or paragraph boundariesStructured deal context

Treat these as starting strategies. Test sizes and overlap; keep text, provenance, and permissions together.

Private searchable storage

03-01

Choose embedding and indexing components by evidence

Embedding configuration

  • Run locally with no external inference calls.
  • Check financial-text performance and input limits.
  • Use compatible query and document encoding; follow required model prefixes.
  • Track model versions and plan index migration.

Searchable index

  • Store vectors, chunk text, provenance, and permissions.
  • Require access filtering and dense plus keyword retrieval.
  • Benchmark latency and storage at expected scale.
  • Self-hosted Qdrant or Weaviate are candidates, not automatic guarantees.
BGE/E5 families are candidate encoders. Select a tested checkpoint and chunk size; do not assume every model accepts long chunks.

Access enforcement

03-01

Permission checks must precede model context

Resolve identity

Use the authenticated principal and current effective access.

→

Filter candidates

Apply the authorization predicate to every retrieval route.

→

Verify freshness

Handle permission changes and revoked access before selecting context.

→

Pass permitted evidence

Only authorized chunks reach reranking and generation.

Permissions follow the document

Attach effective access metadata to each chunk. Account for direct and inherited access rules, not only a simple group list.

Sync is necessary, but not sufficient

Refresh ACLs separately from content embeddings. Define revocation handling and fail closed when access cannot be verified.

Do not retrieve everything and ask the language model to hide the restricted content.

Dense search, keywords, and reranking

03-01

Hybrid retrieval serves different question patterns

Dense retrieval

Embedding similarity finds related meaning even when the question and document use different words.

Useful for conceptual research questions.

Sparse retrieval

BM25 ranks keyword matches using term statistics.

Useful for citation numbers, ticker symbols, and exact deal names.

Fusion & optional reranking

Combine rankings or normalized scores, then optionally re-score question–chunk pairs with a local cross-encoder.

Select a tested top-K within the context budget.

Apply the same access predicate to both searches. Tune fusion and reranking against labeled questions and latency requirements.

Answer generation

03-01

Generate an answer the user can verify

Local model & bounded context

Select an approved instruction-tuned model that fits available compute. Reserve space for instructions, evidence, the query, and output.

Evidence-based instructions

Answer from the retrieved material. Cite important claims. State when evidence is missing, conflicting, or insufficient.

Useful citations

Include document name, version, and a source location such as a section or page. Preserve source links the user is authorized to open.

Retrieved text is evidence, not a new instruction authority. Citations must actually support the associated claims.

Illustrative example

03-01

Walk one compliance question through the design

Question: “What approvals are required before publishing a research note?”

Authenticate

Resolve the employee’s current policy access.

→

Retrieve & rank

Find authorized policy sections using meaning and exact terms.

→

Generate & cite

Summarize the relevant approval steps with policy section and version.

→

Handle a gap

If evidence is incomplete, say so and route to the established owner.

Permission boundary

A restricted deal memo never enters context, even if it contains similar terminology.

Quality boundary

The response reports what the permitted policy supports. It does not invent bank policy or fill missing steps from model memory.

This is a teaching example, not an assertion about the bank’s actual approval policy.

Three dimensions of quality

03-01

Evaluate retrieval and answers separately

Faithfulness

Are the answer’s claims supported by the retrieved evidence?

A local model judge can help screen cases, but its judgments need validation.

Retrieval relevance

Did the system retrieve the passages needed for the question?

Build a golden set of questions and reference evidence across all three user groups.

Completeness

Does the answer cover what that user actually needs?

Use expert review by role; a faithful answer can still miss an important requirement.

Also test access isolation, revoked permissions, freshness, abstention, end-to-end latency, and cost.

FDE delivery plan

03-01

Deliver a measurable slice, then expand

Scope the initial slice

  • Choose a defined user workflow and document subset.
  • Confirm source access, identity mapping, and compute readiness.
  • Agree answer format and role-specific success criteria.

Pilot the complete path

  • Test parsing, chunking, retrieval, citations, and permissions.
  • Measure realistic data volumes and peak concurrency.
  • Include revoked access, stale documents, and insufficient evidence.

Hand off operation

  • Connector and index configuration; model versions.
  • Refresh and permission-sync ownership.
  • Evaluation set, trace examples, recovery procedures, and support owner.
Each design decision should trace back to a workflow, source characteristic, or customer constraint.
