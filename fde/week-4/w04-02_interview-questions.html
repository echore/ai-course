Retrieval design

Interviewers ask questions across the retrieval layer of a RAG system, covering areas like search method, reranking, chunking strategy, and query transformation. Answering well means explaining the concept and naming the tradeoff or benefit clearly. The questions below are for practice. Try answering each one on your own first, then click "Show Answer" to compare.

Q01

When would you choose hybrid search over semantic search alone, and how does the combination work mechanically?

#
Show AnswerHide Answer

Hybrid search combines dense vector retrieval with sparse keyword retrieval. The dense component embeds the query and returns chunks by cosine similarity against the vector index. The other sparse component, typically BM25 (Best Match 25), scores chunks by term frequency and document frequency, favoring exact keyword matches. The two ranked lists are merged using score fusion.

Reciprocal Rank Fusion (RRF) is a common method. It sums the reciprocal of each chunk’s position across both ranked lists, which makes it robust to score scale differences between the two systems.

Dense retrieval fits queries where the question and document use different vocabulary. BM25 fits lookups where specific exact terms must appear in the result. Hybrid search is chosen when the query distribution spans both patterns.

Q02

Why is a cross-encoder used as a reranker rather than a bi-encoder?

#
Show AnswerHide Answer

A bi-encoder embeds the query and each document independently. Document embeddings are pre-computed and stored, so retrieval is fast. The limitation is that similarity is measured in embedding space, not against the specific content of the query.

A cross-encoder takes the query and a candidate chunk as a pair and scores them jointly, attending to interactions between the two. This produces higher precision relevance scores but requires re-processing each candidate at query time, which makes it too slow for first-pass retrieval over a large index. The reranker is applied only to the small candidate set returned by the first pass, where its cost is acceptable and its precision gain is highest.

Q03

Your system retrieves 20 candidate chunks but the LLM context window fits only 5. How do you handle this?

#
Show AnswerHide Answer

The standard approach is reranking. A cross-encoder re-scores all 20 candidates by processing each one as a pair with the question, attending to the interaction between question and chunk content. This produces more precise relevance scores than first-pass retrieval, which ranks by embedding proximity rather than answer relevance. The 5 highest-ranked chunks after reranking are more likely to contain the specific information the question needs.

An alternative is reducing chunk size so more chunks fit within the same window, but smaller chunks risk losing the surrounding context that helps the model generate a complete answer.

Reranking is the more targeted approach because it improves which chunks are selected without changing the amount of context each one provides.

Q04

How does parent-child chunking improve retrieval over flat chunking?

#
Show AnswerHide Answer

Parent-child chunking stores each document at two levels. The child chunk, typically a paragraph, is what gets embedded and matched during retrieval. When a child chunk is retrieved, the system passes the parent chunk, typically the full section containing that paragraph, to the model as context. This decouples the unit of retrieval from the unit of context.

Small child chunks produce precise retrieval because they contain fewer unrelated terms. Large parent chunks give the model enough surrounding context to generate a complete answer.

Q05

How does HyDE work, and what is its primary tradeoff in a production system?

#
Show AnswerHide Answer

HyDE (Hypothetical Document Embeddings) generates a hypothetical answer to the query using the LLM before retrieval runs. That hypothetical answer is then embedded and used as the retrieval query instead of the original question.

The reasoning is that a hypothetical answer uses the vocabulary and structure of real documents in the corpus, making it a stronger embedding match than the original question. The primary tradeoff is latency. Each query requires an LLM call before retrieval starts, adding to overall response time.

HyDE is most valuable when there is a significant vocabulary gap between how users phrase questions and how documents are written. When queries already use the exact terms present in the corpus, the added latency of the extra LLM call outweighs the retrieval gain.

With retrieval design covered, the natural next area is how to measure whether these choices are working and what to do when they are not.

Evaluation and debugging

The interviewer might ask about metric interpretation, how to identify where in the pipeline a failure originates, how to set ground truth for retrieval, or when to prioritize one measure over another. Q06

How would you detect whether a bad answer came from poor retrieval or poor generation?

#
Show AnswerHide Answer

The diagnostic is to inspect the retrieved chunks directly. If the chunks returned for a query do not contain the information needed to answer it, the failure is in retrieval. If the chunks contain the correct information and the answer is still wrong, the failure is in generation.

In practice, we log retrieved chunks alongside answers and build an evaluation set of known question-answer pairs with known source documents. For each failing answer, we check whether the ground-truth source document appeared in the retrieved set. If it was absent, we tune retrieval parameters. If it was present and the answer is still incorrect, we address the generation prompt or model behavior.

Q07

Your system achieves high context precision but low faithfulness. How do you diagnose and fix it?

#
Show AnswerHide Answer

High context precision means the retrieved chunks are relevant to the question. Low faithfulness means the generated answer contains claims not supported by those chunks. The gap is in generation. The model is drawing on pretraining knowledge or combining retrieved chunks in ways that introduce unsupported inferences.

The fix is in the system prompt. The prompt must instruct the model to answer only from the retrieved context and to state explicitly when the context does not contain enough to answer.

Adding an LLM-as-judge faithfulness check surfaces which answer types fail most frequently and whether the problem is concentrated in specific query categories or document sources.

Q08

Your retriever has high context precision but low context recall. What query types suffer most and why?

#
Show AnswerHide Answer

High precision with low recall means returned chunks are relevant but the retriever is missing other relevant chunks that should have been included.

The queries that suffer most are those where the answer is distributed across multiple documents. The retriever returns one precise chunk and misses the others that also contain relevant content. Queries where the relevant content uses different vocabulary than the query also suffer, because dense retrieval alone misses them.

Increasing the candidate pool before reranking addresses distributed answers, and hybrid search addresses vocabulary mismatch.

Understanding what fails at the retrieval and generation layer prepares us for the harder production questions, where constraints from the real enterprise environment add new failure modes.

Production and enterprise constraints

Production questions shift the conversation from system design to what happens once the system is running in a real enterprise. The interviewer might ask about permission enforcement at scale, handling document versioning and conflicts, how source system changes affect the pipeline, or whether architectural assumptions hold as model capabilities evolve. The questions below are for practice. Try answering each one on your own first, then click "Show Answer" to compare.

Q09

How do you implement per-user access control in an enterprise RAG system without querying source permissions on every request?

#
Show AnswerHide Answer

Permission checking moves from query time to index time. When a document is ingested, its ACL is stored as metadata on every chunk derived from that document.

At query time, the user’s identity is resolved to their current group memberships through the identity provider, and a metadata filter is constructed from those memberships. The vector search runs with the filter applied, so only chunks the user is permitted to access are candidates.

A background sync job re-fetches ACLs from each source system on a schedule and updates chunk metadata when permissions change. The retrieval step is never slower due to permission enforcement, and no source system is queried during a user request.

Q10

Your enterprise RAG returns contradictory answers derived from two different documents on the same topic. How do you handle this?

#
Show AnswerHide Answer

The first response is transparency. The system surfaces both sources and their claims rather than silently selecting one. Citation metadata includes the document version date or last modified timestamp so the user can assess which source is more current or authoritative.

Beyond that, the ingestion pipeline can track document lineage and flag superseded versions of the same document, reducing how often outdated versions appear in retrieval.

For documents where contradiction reflects genuine analytical disagreement, the system prompt instructs the model to note when retrieved sources disagree and to present both positions with their citations, rather than synthesizing a false consensus.

Q11

Is RAG still the right architecture when the LLM supports a one million token context window?

#
Show AnswerHide Answer

For most enterprise knowledge bases, yes. A one million token window can hold substantial text, but a corpus spanning millions of chunks across multiple document sources exceeds that limit. Fitting the full corpus into a single context call is not feasible, and doing so for every query would produce prohibitive latency and compute cost even if it were possible.

RAG also resolves access control requirements that long context alone cannot address. A system that passes the full corpus to the model cannot scope what the model sees to only what the requesting user is permitted to access. Retrieval makes permission filtering both precise and efficient.

Long-context windows are most valuable in combination with RAG, where they allow more retrieved chunks to be passed in context and reduce the precision pressure on reranking.

Adapting to new requirements

Sometimes the interviewer introduces a change to the case study or the system just designed and asks how the architecture would need to adjust. The change could involve a new user group, an additional data source, a tighter latency requirement, or a new compliance rule. The goal is to trace which components are affected and what ripples from there. The questions below are for practice. Try answering each one on your own first, then click “Show Answer” to compare.

Q12

The Hong Kong office analysts want to query the system in Mandarin. Documents in the corpus remain in English. What changes in the architecture?

#
Show AnswerHide Answer

The current embedding model maps only English text to the vector space. A multilingual embedding model such as multilingual-E5 maps queries and documents from different languages into the same shared vector space, enabling cross-lingual retrieval. A Mandarin query can retrieve English chunks without a translation step.

Switching to a multilingual model requires a full re-index of the corpus because the new model produces a different vector representation for every chunk. The BM25 sparse index also requires adjustment. BM25 is language-specific and a Mandarin query will not match English terms, so for Mandarin queries the hybrid retrieval weight should shift toward the dense component.

On the generation side, the system prompt instructs the model to respond in the same language as the query, which a multilingual instruction-tuned model handles without further changes. The permission model, connectors, and chunking strategy are unchanged.

Q13

The compliance team requires that if the system is not confident in its answer, it must decline to respond and route the query to a human expert instead. What changes in the architecture?

#
Show AnswerHide Answer

A confidence gate is added between generation and delivery. Two signals inform the gate.

The first is retrieval confidence. If the highest-scoring chunk falls below a defined threshold, retrieval did not find strong support and the query is flagged before generation runs, avoiding the cost of an LLM call. The second is a faithfulness self-check. After generation, the model is prompted to assess whether its answer is fully grounded in the retrieved chunks.

If either signal indicates low confidence, the system returns a fallback response and logs the original query, retrieved chunks, and routing reason to a human expert queue. The confidence threshold is not uniform across user groups. Compliance officers require a lower tolerance for uncertainty than research analysts, so the threshold for routing compliance queries is set more conservatively. Routed queries in the expert queue also become labeled examples that expand the evaluation dataset over time.

Q14

How would you scope a two-week POC for this system, and what would you cut?

#
Show AnswerHide Answer

A two-week POC proves the hardest technical unknowns, not the full system. For the knowledge assistant, the two hardest unknowns are retrieval quality on the bank’s actual documents and whether the permission pre-filter produces correct results across user groups.

The POC scopes to one document source, SharePoint, with a representative subset of document libraries covering each user group. The embedding model, vector store, and permission filter are all in scope. The email archive connector, file server connector, OCR processing, and the full evaluation framework are cut.

The output is a working end-to-end flow covering ingestion, chunking, embedding, permission filtering, retrieval, generation, and citation. The bank’s team tests it with real queries and the findings shape the full build scope.

Q15

What are the highest handoff risks for this system, and how would you surface them before the engagement ends?

#
Show AnswerHide Answer

Three risks stand out.

The first is the permission sync job. If it fails silently, ACL metadata becomes stale and users may receive answers derived from documents they should not access. The customer’s team needs a monitoring signal on this job and a remediation runbook.

The second is embedding model drift. If the bank’s infrastructure team updates the embedding model without re-indexing existing chunks, query embeddings and chunk embeddings will no longer occupy the same vector space and retrieval quality will degrade without an obvious error.

The third is silent ingestion gaps. If a new SharePoint site is added or a file server directory is reorganized, the connectors may miss new content without surfacing an error.

Each risk should appear in handoff documentation with a specific monitoring signal and a remediation step, not as a general warning but as a named failure mode.

Technical interview questions reward answers grounded in the specific system. Naming the exact component that changes, the metric that surfaces a failure, or the risk that appears after handoff carries more weight than describing the same concept in general terms. The system design provides that grounding; the questions measure whether we can draw on it.
