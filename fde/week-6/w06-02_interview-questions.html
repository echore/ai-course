Fine-tuning decision making

Fine-tuning decision questions test whether we understand when fine-tuning is genuinely justified and what should be tried first. Interviewers look for a decision framework grounded in the problem, not a reflex toward the most sophisticated tool. The questions below are for practice. Try answering each one on your own first, then click “Show Answer” to compare.

Q01

When would you choose fine-tuning over prompting to close an accuracy gap? What signals tell you prompting has hit its ceiling?

#
Show AnswerHide Answer

Three signals, appearing together, point toward fine-tuning.

  • First, the error pattern is behavioral rather than factual. The model understands the task but does not produce outputs in the format or style the use case requires.
  • Second, few-shot examples in the prompt improve accuracy on the demonstrated cases but do not generalize to new inputs, which means the model is not learning the underlying pattern.
  • Third, the gap between the baseline result and the target is large enough that no reasonable number of additional prompt examples would close it.

When those signals appear and labeled examples from the target domain exist, fine-tuning is a candidate for the next experiment, evaluated against the prompting baseline.

Q02

Walk us through your decision framework for choosing between prompt engineering, RAG, and fine-tuning for a new enterprise task.

#
Show AnswerHide Answer

We work through these in sequence, not all at once.

We start with prompt engineering. A well-structured prompt with clear instructions and a few examples is the fastest and cheapest approach. We measure how far it gets us before considering anything else.

If the gap remains and the task involves retrieving or grounding answers against a document corpus the model was not trained on, we add RAG. However, RAG addresses knowledge gaps and does not update the model’s weights, although retrieved context can influence its responses.

If the gap is behavioral, meaning the model needs to learn a specific output style, domain terminology, or task format that cannot be conveyed through instructions and examples alone, we move to fine-tuning. In this framework, fine-tuning follows simpler baselines. RAG and fine-tuning can also be combined when the task has both knowledge and behavioral gaps.

Q03

Can fine-tuning add new factual knowledge to a model, or does it only change how the model behaves?

#
Show AnswerHide Answer

Fine-tuning can change behavior and teach some factual associations, but it is not a reliable replacement for an updatable knowledge source. It teaches the model to apply patterns from the training data, such as output format, style, or domain-specific conventions, but it does not reliably inject new facts. Factual associations learned from a small fine-tuning dataset may not generalize reliably, and the model can hallucinate confidently on facts not covered in training. When the gap is in how the model produces output, fine-tuning fits. When the gap is factual, RAG is often the better starting point, especially when facts change or answers need source evidence.

Q04

A colleague argues that adding well-chosen few-shot examples to the prompt would be faster and cheaper than fine-tuning. How do you evaluate that argument?

#
Show AnswerHide Answer

The argument is often correct, which is why we test it first. The case for prompting holds when the task is well-defined, the target format can be demonstrated in a handful of examples, and the model’s general capability already covers the domain.

The case for fine-tuning holds when:

  • The prompt with examples still shows high variance across input types that were not explicitly shown as examples.
  • The target output pattern is too complex or numerous to fit usefully in a context window.
  • Consistent performance at scale is required, and prompt-based solutions degrade on edge cases the examples did not cover.

We run the few-shot approach and compare its results to the zero-shot baseline. If the improvement is substantial and the residual gap is small, we stay with prompting. If a large gap remains, we have evidence that justifies the fine-tuning investment.

The next set of questions tests whether the training data is good enough to learn from, which determines whether fine-tuning works at all.

Training data

Training data questions test whether we know what makes a dataset usable and what happens when preparation is rushed. Interviewers look for specific answers about annotation quality, data splits, and common mistakes that silently degrade model performance. The questions below are for practice. Try answering each one on your own first, then click “Show Answer” to compare.

Q05

How do you structure a training example for a structured output task where the input is a document and the output is a fixed-format extraction?

#
Show AnswerHide Answer

Each training example needs three components: a consistent input format, a consistent output format, and a system-level instruction that tells the model what the task is.

The input is the document text, cleaned and formatted the same way it will appear at inference time. The output is the extraction result in the exact structure the production system expects. The system instruction specifies what the model is supposed to do and what format it must return.

Consistency between training and inference is the most important property. If the input format at inference time differs from what the model was trained on, performance can degrade. Test preprocessing and formatting changes before releasing them.

Q06

Some examples in our dataset were corrected or relabeled after the original annotation. How do we decide which ones to keep?

#
Show AnswerHide Answer

We check why the relabeling happened before deciding.

If the correction fixed a clear error in the original label, we keep the corrected version and discard the original. Including both teaches the model to produce two different outputs for the same or similar input, which it cannot resolve consistently.

If the relabeling reflects genuine ambiguity where two experienced annotators reasonably disagreed, we ask an expert to adjudicate it against the annotation guidelines. If it remains unresolved, we exclude it from this fixed-output training set. Training on ambiguous labels teaches inconsistent behavior.

If we cannot determine why the relabeling happened, we exclude the example. A smaller, clean dataset can produce a better-behaved model than a larger dataset with uncertain label quality.

Q07

A teammate suggests using the held-out test set, a set of labeled examples set aside before training begins and never used during training or validation, to monitor training progress and retraining if accuracy drops. What is wrong with that approach?

#
Show AnswerHide Answer

It turns the test set into a training signal. Once the test set is used to make any decision during training, such as when to stop or whether to add more data, the final accuracy measurement on that set is no longer trustworthy. The model has indirectly been optimized toward the test set, which means the reported accuracy overstates real-world performance.

The test set should be set aside before training begins and used for final evaluation after the design and training choices are fixed. If its results guide another round of model changes, use a fresh untouched test set for the next final estimate. Monitoring during training uses the validation set, which is separate from both the training set and the test set.

Q08

After training, the model performs well on one subset of the training distribution but poorly on another, despite equal representation in the training set. What are the most likely causes?

#
Show AnswerHide Answer

Equal representation does not mean equal difficulty or equal label quality. Three causes are worth investigating.

  • Label inconsistency in the harder subset: If annotation guidelines were applied differently across subsets, the model learns inconsistent patterns. The subset with cleaner labels produces better results.
  • Higher surface variation in the harder subset: If one subset contains more diverse phrasing, longer inputs, or more edge cases, the model needs proportionally more examples to generalize, even if the count is nominally equal.
  • Domain gap from pretraining: One subset may be closer to the base model’s pretraining distribution, giving the model a head start. The other subset may require more behavioral change than the training data size supports.

The first step is to audit a sample of the low-performing subset’s labels and compare them to the high-performing subset before changing anything else.

Fine-tuning method selection

Method selection questions test whether we understand LoRA and QLoRA at a mechanical level, not just in concept. Interviewers often include one or two genuinely tricky questions here to separate candidates who have worked with these methods from those who have only read about them. The questions below are for practice. Try answering each one on your own first, then click “Show Answer” to compare.

Q09

How does LoRA reduce memory usage compared to updating all model parameters?

#
Show AnswerHide Answer

In full fine-tuning, every parameter in the model accumulates a gradient and an optimizer state during training.

LoRA freezes all of the base model’s parameters and adds a pair of small matrices, A and B, to specific layers. Only these added matrices are trained. The product of A and B, with a scaling factor, represents a learned low-rank weight update; it is not guaranteed to match a full fine-tuning update. Because the base model’s parameters receive no gradients, their optimizer states are never computed. This greatly reduces gradient and optimizer-state memory. Base weights, activations, and temporary computation still consume memory, so total savings depend on the model and training setup.

Q10

What does the rank parameter r in LoRA control, and what are the practical consequences of setting it too high or too low?

#
Show AnswerHide Answer

The rank r determines how many dimensions the weight update can span. A higher rank gives the adapter more capacity to represent complex adjustments; a lower rank constrains it to simpler ones.

Setting r too low means the adapter cannot capture the full complexity of the behavioral change the task requires. The model may stall at a lower accuracy than it would reach with more capacity.

Setting r too high increases the number of trainable parameters, which raises memory usage and overfitting risk, particularly on small datasets. For this example, ranks such as 4, 16, and 64 are candidates to compare; r=16 is a starting experiment, not a universal default. Use validation results to test capacity, alongside learning rate, training duration, and data quality. An early plateau alone does not prove the rank is too low.

Q11

How do adapter layers differ from LoRA at inference time, and why does that difference matter for a production system?

#
Show AnswerHide Answer

Adapter layers are sequential modules inserted inside the transformer block. At inference time, every forward pass must run through those modules, which adds computational overhead to every token generated.

LoRA adapters can be merged into the base model’s weights after training. The merge operation adds the scaled low-rank product of the two adapter matrices to the original weight matrix, producing a new matrix with the same shape. Once merged, the production model is identical in structure to the original base model and the extra adapter computation is removed. For a production system serving many requests under latency constraints, removing adapter overhead can make LoRA practical. Check that the serving and quantization setup supports merging, and benchmark the deployed model’s quality and latency.

Understanding how to select and train a fine-tuned model matters, but knowing how to measure whether it actually works is what determines whether it reaches production.

Evaluation

Evaluation questions test whether we can define the right metrics, build a trustworthy test set, interpret what the numbers mean, and explain performance clearly to non-technical stakeholders. Interviewers look for precise answers, particularly on stopping criteria and production drift. The questions below are for practice. Try answering each one on your own first, then click “Show Answer” to compare.

Q12

How do you evaluate a fine-tuned model on a structured output task where there is both a field-level metric and a full-record metric? Which matters more and to whom?

#
Show AnswerHide Answer

We measure both and report them separately because they answer different questions.

Field-level accuracy measures the percentage of individual output fields the model gets correct. It tells engineers and data scientists where the model struggles: which field types, which input patterns, and which edge cases produce the most errors. This is the diagnostic metric used to drive improvement.

Full-record accuracy measures the percentage of complete outputs where every field is correct. A record is either fully correct or it fails. This maps directly to the business outcome: whether the downstream system accepts or rejects the output. This is the metric stakeholders care about.

It is possible to have high field-level accuracy and low full-record accuracy if errors distribute across different records. That gap is important to surface early because it means field-level improvements are not translating into business value.

Q13

Training loss keeps falling but validation loss levels off and starts to rise slightly. What is happening and what do we do?

#
Show AnswerHide Answer

The model is beginning to overfit. It is memorizing the training examples rather than learning patterns that generalize to new inputs.

We use early stopping with a predefined validation criterion and select the best checkpoint. Validation loss is useful, but for structured extraction we also check the task metrics that govern deployment. A slight rise can be noise; a sustained divergence is stronger evidence of overfitting. If this happens consistently and too early in training, it usually signals the training dataset is too small, too uniform, or that the learning rate or LoRA rank is set too high for the available data.

Q14

A fine-tuned model scores well on the held-out test set but performs significantly worse in production after a few weeks. What are the most likely causes?

#
Show AnswerHide Answer

We investigate these plausible causes before touching the model; the evidence determines the priority.

  • Distribution shift: The inputs in production have drifted from the training and test distribution. Documentation styles, terminology, or input formats may have changed.
  • Input format changes: A small change to how the input is formatted before being sent to the model can degrade performance significantly even when the underlying task has not changed.
  • Test set contamination: If the test set was used to make any training decision, the evaluation result overstated real-world performance. Production becomes the first honest test.
  • Label drift: The correct output has changed because the underlying guidelines or standards were updated, but the model was trained on the previous standard.

We start by sampling production failures and comparing them against the test set to determine which cause is primary before making any changes.

Q15

What is capability regression in fine-tuning and how do we test for it before deploying to production?

#
Show AnswerHide Answer

Capability regression is when a fine-tuned model loses general abilities it had as the base model, such as instruction following, reasoning on unfamiliar inputs, or basic language fluency. It happens when the fine-tuning dataset is narrow enough that training pulls the model too far from the general distribution it was pretrained on.

We test for it by running the fine-tuned model against a set of general capability checks alongside the task-specific evaluation. The checks can include reasoning tasks, format-following tasks, and edge case inputs the training data did not contain. If the fine-tuned model performs noticeably worse than the base model on those, we have capability regression. One possible mitigation is to mix a small proportion of general-purpose examples into the training data to anchor the model’s general abilities while it learns the task-specific patterns.

Changing requirements

Changing requirements questions test whether we understand the reasoning behind each design decision well enough to revise it when the context shifts. Interviewers use these to find candidates who understood the why, not just the what. The questions below are for practice. Try answering each one on your own first, then click “Show Answer” to compare.

Q16

If the hospital’s privacy and procurement requirements allowed it to send notes to an approved commercial API, would fine-tuning still be the right approach for this task?

#
Show AnswerHide Answer

Not necessarily. In this case, the hospital’s private-deployment requirement constrained the model options; HIPAA itself does not universally require self-hosting. An approved cloud service can be an option with an appropriate business associate agreement and applicable safeguards. If commercial models become eligible, benchmark them on this task rather than assuming they perform better. Deployment eligibility alone does not establish that fine-tuning is necessary.

With a commercial API available, the right first step would be to test a strong few-shot prompt with confirmed coding examples against the 95% target. If a commercial model reaches the target through prompting, the fine-tuning investment may not be justified.

Fine-tuning would still be the right call if the hospital’s physician note style or modifier code conventions are unusual enough that even a commercial model cannot reach the target with prompting alone. But that is an empirical question to test, not an assumption to carry forward.

Q17

The hospital tells us they only have 120 confirmed coded encounters available for training. How does that change our approach?

#
Show AnswerHide Answer

We adjust in three ways.

  • First, we test a lower LoRA rank to reduce the adapter’s capacity and overfitting risk. With few examples, a high-rank adapter can memorize the training set rather than generalizing.
  • Second, we protect a representative final test set and use validation or cross-validation on the remaining development data. With only 120 examples, a tiny test set gives an unstable estimate; we report that uncertainty and seek more confirmed labels before claiming the production target is met.
  • Third, we run a strong few-shot prompting baseline before committing to fine-tuning. With only 120 examples, the difference in performance between a well-designed prompt and a fine-tuned adapter may not justify the annotation and training overhead. For a hypothetical example, if prompting reaches 88% and fine-tuning reaches 91%, the question becomes whether that 3-point gain is worth the investment at this dataset size.
Q18

Six months after deployment, the hospital adopts a new set of modifier code guidelines. How do we update the system?

#
Show AnswerHide Answer

We collect newly labeled encounters coded under the new guidelines and produce a fresh training dataset. We do not mix old-guideline examples with new-guideline examples in the same training run because the model would learn conflicting patterns for the same input types.

Because the change affects modifier code rules rather than the underlying note style or diagnosis code mapping, we may not need to retrain from the base model. Training a new LoRA adapter on the updated examples and evaluating it against the target is often sufficient. If it reaches the accuracy threshold, we replace the deployed adapter without touching the base model.

The coder review step remains in place throughout. During the transition, we can flag modifier codes specifically for closer coder attention until the new adapter is validated.

Q19

The hospital wants to extend the system to a second facility with different physicians and a different documentation style. What additional work is required?

#
Show AnswerHide Answer

We treat the second facility as a new scoping and validation exercise. Reusing the existing model is an option only after testing it on that facility’s data.

We work through the same clarifying questions from the original engagement. How many confirmed coded encounters does the second facility have? How different is their physician note style? Do they follow the same modifier code guidelines?

If the styles are similar enough and the second facility has sufficient labeled data, we first evaluate the current adapter. If it misses the target, we can train a new adapter on their data using the same base model and pipeline. If the styles are very different, we evaluate whether a combined adapter trained on data from both facilities performs adequately for each, or whether separate adapters are required. Mixing dissimilar data without enough examples from each can produce a model that generalizes poorly to both facilities.

The FDE questions that follow test how we apply this reasoning in conversation with the customer.

FDE role-specific questions

FDE questions on a fine-tuning system are not purely technical. They test whether we can communicate design decisions to non-technical stakeholders, investigate production issues without jumping to the wrong fix, and scope extensions without underestimating complexity. The questions below are for practice. Try answering each one on your own first, then click “Show Answer” to compare.

Q20

The coding director asks why we chose QLoRA over full fine-tuning. How do we explain the decision without technical jargon?

#
Show AnswerHide Answer

We chose the approach that matches the size of the change we are actually making.

Full fine-tuning updates every part of the model, which is like renovating an entire building when we only need to adjust a few rooms. It requires significantly more computing resources, can take longer, and requires careful control of overfitting on a small dataset. Updating fewer parameters also does not eliminate overfitting risk.

QLoRA makes a smaller, more targeted set of changes while leaving the rest of the model untouched. It reduces training-memory requirements by using a compressed, frozen base model and training a small adjustment. We store that adjustment separately and test whether the adapted model learns the hospital’s coding patterns while retaining the general abilities the workflow needs. When the hospital’s billing guidelines change, we update only that stored adjustment rather than retraining everything from scratch.

Q21

A coder on the hospital’s team tells you that reviewing the AI suggestions is taking longer than coding from scratch used to. How do you investigate and respond?

#
Show AnswerHide Answer

We take this seriously. If review is slower than the original workflow, the system is creating friction rather than removing it.

We start by sitting with the coder and observing how they use the interface. We ask whether the suggestions are usually close to correct or whether they are wrong often enough that the coder discards them and recodes each encounter from scratch. Those two cases have different causes.

If the suggestions are frequently wrong, accuracy needs to improve before the workflow helps anyone. We pull the coder’s correction logs to identify the pattern and bring it back to the model evaluation.

If the suggestions are directionally correct but the interface is slow to navigate or the code attribution display is hard to read, the problem is in the integration design. We identify which steps in the Epic coding screen add the most time and fix those before touching the model.

The broader point is that adoption failures matter as much as accuracy failures. A system that coders distrust or work around does not improve the first-pass rate regardless of what the test set showed.

Q22

The hospital CFO asks what happens if the AI suggests a wrong code and the coder confirms it without reviewing carefully. How do we respond?

#
Show AnswerHide Answer

We acknowledge the risk directly and explain what the design does to reduce it.

The system cannot eliminate the possibility of a coder confirming a wrong code. What it does is make careful review easier than it was before. Each suggested code appears alongside the specific phrase in the physician note that supports it. The attribution helps the coder locate evidence, but does not prove that a code is correct or replace reviewing the clinical context and applicable coding rules.

Beyond the interface, the audit log records every AI suggestion and every coder decision. If a pattern of wrong confirmations appears, the hospital can identify which code types are being confirmed incorrectly and use that data to improve both the model and coder review training.

The broader accountability point is that the workflow retains coder review and confirmation, with the hospital defining review responsibilities and escalation procedures. The AI suggestion is a starting point. The coder’s decision is still the decision.

Q23

A second hospital in the network asks whether they can use the same model. How do we frame that scoping conversation?

#
Show AnswerHide Answer

We ask the same clarifying questions we asked at the first hospital before giving any estimate.

We ask how similar their physician note style is to the first hospital’s. We ask how many confirmed coded encounters they have available. We ask whether they follow the same modifier code guidelines and what their current first-pass rate is.

Depending on the answers, the options are:

  • Reuse the existing adapter: If their note style and coding practices are similar, we evaluate the current model on a sample of their encounters. If it meets the target, no retraining is needed.
  • Train a new adapter: We use the same base model and pipeline with their labeled data.
  • Train a combined adapter: If both hospitals want a shared model, we train on the combined dataset and validate separately for each facility.

Separating these options early prevents the second hospital from assuming the same timeline and budget apply.

Preparing for these questions builds something beyond recall. Working through the reasoning behind each decision, whether about data preparation, method selection, or how to respond when a stakeholder pushes back, develops the kind of fluency that holds up when an interviewer follows up with a harder version of the same question.
