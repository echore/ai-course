The customer problem

06-01

The hospital needs more reliable coding proposals

A regional hospital and its outpatient clinics use Epic. Coders translate physician notes into diagnoses, procedures, and modifiers.

81% · Current workflow

Reported first-pass payer acceptance with human coding. Denials create rework.

61% · Model baseline

Reported unadapted-model result on 200 encounters. The accuracy definition needs confirmation.

95% · Scenario target

A desired outcome to define and test, rather than a verified industry benchmark.

Documentation enters Epic.

Coding accuracy and payer acceptance are different measures; compare results only when their definitions match.

Questions before architecture

06-01

Discovery establishes what success means

Turn “improve coding” into an output contract, a usable dataset, and an operational acceptance test.

Task and target

  • One code set or ranked alternatives?
  • Per-code accuracy or a completely correct encounter?
  • Which corrections are captured?

Data and coverage

  • How many confirmed encounters exist?
  • Which specialties and note styles are represented?
  • Which guideline versions apply?

Errors and priorities

  • Missing diagnoses, wrong procedures, or modifiers?
  • Which departments drive denial rework?
  • Which mistakes carry the greatest cost?

Deployment and ownership

  • Available GPUs and required response time?
  • Where does review fit inside Epic?
  • Who approves releases and refreshes?
The answers determine the first delivery scope, label requirements, evaluation slices, and deployment budget.

Problem decomposition

06-01

Six responsibilities turn the request into a system

Assign inputs, outputs, and owners before deciding which model or training method to use.

01 · Prepare labels

Pair notes with adjudicated code sets; retain provenance and guideline versions.

02 · Choose the approach

Test prompting, retrieval or rules, and adaptation against the observed errors.

03 · Select a base model

Check note length, license, structured output, and hardware fit.

04 · Adapt the model

Train and compare checkpoints using a controlled data split.

05 · Evaluate the result

Measure code quality and encounter correctness before promotion.

06 · Integrate review

Show proposals in Epic; capture confirmation, corrections, and audit records.

Fine-tuning is one responsibility within the delivery; data quality and workflow integration remain essential.

Prompting, retrieval, or adaptation

06-01

The approach follows the error pattern

Fine-tuning updates model parameters from examples. It should earn its place against simpler baselines.

ApproachWhat it can improveWhat to test
Prompting / few-shot examplesTask instructions, output format, and demonstrations without changing weights.Can a better prompt reduce the recurring errors?
Retrieval + coding rulesAccess to current guidelines, code catalogs, and rule-based checks.Does missing or outdated information explain the failures?
Fine-tuningRepeated mapping from local note styles to consistent structured code sets.Do confirmed labels produce a held-out gain over the same base model?
These approaches can be combined. A poor baseline does not prove that fine-tuning is required or will reach 95%.

Training record

06-01

Each example connects a note to a confirmed code set

Use a consistent input/output format. This field outline is illustrative, not a medical coding recommendation.

Input · Encounter note

  • Physician narrative and relevant clinical context.
  • Specialty and note format where needed.
  • Allowed context within the chosen model’s token limit.

Target · Confirmed result

Data preparation

06-01

Label quality controls what the model learns

Cleaning should remove unreliable supervision while preserving valid difficult encounters.

Confirm the final label

  • Use the approved diagnosis, procedure, and modifier set.
  • Preserve provenance and measure agreement between labelers.

Resolve uncertainty

  • Adjudicate revised or disputed encounters.
  • Exclude unresolved labels; keep difficult cases once confirmed.

Check coverage and currency

  • Represent specialties and typed / dictated note styles.
  • Track guideline dates and inconsistent labeling conventions.
Apply consistent annotation guidance and review a sample of note–label pairs before training.

Dataset boundaries

06-01

Separate learning, selection, and final testing

Create the splits before training; prevent patients and near-duplicate notes from crossing boundaries.

Training set

Updates the selected trainable parameters. Covers the note styles and code patterns in scope.

Validation set

Selects settings and checkpoints. Guides early stopping without training on these examples.

Locked test set

Measures the final candidate once selection is complete. Includes relevant specialties and later encounters.

Group related encounters and duplicates appropriately; use temporal and department slices to expose leakage or weak coverage.

Model selection

06-01

The base model must fit the task and the GPUs

Evaluate exact checkpoints locally rather than selecting a model family by reputation.

Long-note coverage

  • Measure actual input and output token lengths.
  • Define handling for notes beyond the supported context.
  • Avoid silent truncation of coding evidence.

Training and serving capacity

  • Budget weights, activations, and optimizer state.
  • Measure inference cache and concurrency separately.
  • Benchmark the hospital’s available GPUs.

Behavior and deployment rights

  • Test instruction following and valid structured outputs.
  • Check the exact checkpoint’s license and terms.
  • Compare quality with the same data and prompt.
The source names Llama, Mistral, Phi, and Gemma candidates. Each exact version still needs task, license, and hardware checks.

Adaptation choices

06-01

Fine-tuning methods update different parameter sets

The amount of trainable state affects memory, storage, and the experiment budget.

MethodWhat changesPractical tradeoff
Full fine-tuningAll base-model parameters are trainable.Largest training-state cost; evaluate whether the added flexibility is needed.
Partial fine-tuningSelected layers or parameters are trainable.Reduces trainable state, but performance depends on which parts are selected.
LoRABase weights stay frozen; small low-rank update matrices are trained.Smaller trainable adapters; target modules and rank are experiment choices.
Low-rank adapters reduce trainable state. They still need representative labels, validation, and hardware measurements.

Memory-efficient adaptation

06-01

QLoRA combines a quantized base with an adapter

QLoRA trains LoRA adapters through a frozen base model stored in 4-bit precision.

Frozen 4-bit base

Lower-precision storage reduces base-weight memory. The pretrained weights are not updated.

Trainable LoRA adapter

Small update matrices learn from confirmed encounter examples. Save the adapter as a versioned artifact.

Compatible adapted model

  • Load the matching base checkpoint and adapter.
  • Benchmark quality, latency, and memory in the intended serving setup.
4-bit storage reduces one part of memory use. Activations, training state, and inference caches still need capacity.

Training and promotion

06-01

Validation selects the checkpoint; testing permits release

Use a repeatable experiment configuration and task metrics rather than training loss alone.

Train controlled experiments

Track data version, base checkpoint, adapter settings, batch size, learning rate, and token limits.

Select on validation

Watch validation loss and coding metrics. Stop after meaningful improvement stalls; compare candidate checkpoints.

Test and package

Evaluate the chosen candidate on the locked test set. Register base, adapter, data, and guideline versions with a rollback path.

Do not tune repeatedly on the final test set or treat the lowest training loss as production readiness.

Evidence for delivery

06-01

Evaluation separates code quality from claim outcomes

Compare the unadapted, prompted, and adapted systems on the same representative held-out encounters.

MeasureWhat it tells youHow to interpret it
Code-family qualityDiagnosis, procedure, and modifier precision / recall; missing and extra codes.Precision: proposed codes that are correct. Recall: required codes that are found.
Exact code-set correctnessEvery required code and modifier is present, with no incorrect extras.A stricter encounter-level test; report department and note-style slices.
Payer first-pass acceptanceClaims accepted after coder review and billing submission.A downstream business outcome with causes beyond model coding accuracy.
Define the 95% target with the hospital. Report sample size and uncertainty; 200 baseline encounters are a pilot, not proof of broad coverage.

Live coding assistance

06-01

Inference returns a proposal with checkable evidence

Keep the read, generation, validation, and display stages explicit so failures have a defined outcome.

Read

Fetch the authorized encounter note from the approved Epic interface.

Generate

Return structured diagnoses, procedures, and modifiers.

Validate

Check schema, current code catalog, and supporting note spans.

Display

Show proposed codes, evidence, and review flags to the coder.

Evidence attribution

A quote or span must match the actual note. It helps review but does not establish clinical coding correctness by itself.

Explicit fallback

Invalid output, missing support, or a timeout routes the encounter to manual review without automatic claim submission.

Deployment connects four owned components

Evaluation and customer handoff

06-01

Refresh the system when evidence or rules change

A refresh is a controlled release, with a decision about which layer actually needs to change.

Observe the workflow

Monitor coder corrections, specialty quality, payer denial reasons, latency, and guideline changes.

Choose the intervention

Review new labels. Refresh catalogs or retrieval for current rules; retrain only when behavior needs adaptation.

Re-evaluate and hand off

Repeat held-out checks, approve a version, and retain rollback. Give owners the data contract, thresholds, and recovery runbook.

Track base, adapter, data, and guideline versions so the customer can explain a proposal and recover a release.

Reliable adaptation depends on data, proof, and review

Define the target. Learn from confirmed examples. Demonstrate a held-out gain. Keep the coder in control.
