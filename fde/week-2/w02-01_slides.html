The Proof of Concept (POC) Sprint

Testing AI system approaches against real data and customer environments.

Module 02-01  ·  End-to-End Delivery

Definition

02-01

What is a POC?

Customers often expect a proof of concept to be a smaller version of the final product. It is not.

  • A POC is a time-boxed experiment designed to answer one question before committing to a full build.
  • Does this approach work, with this data, inside this customer environment?
  • Everything not required to answer that specific question stays out of scope.
The output of a sprint is an answer, not a product. The Core Objective

Structure

02-01

How a sprint is structured

The length of each stage varies by project, but they should never be skipped.

1
Access & Setup
Confirming all technical dependencies, credentials, and data access are in place.
2
Data Validation
Examining what the data actually looks like versus what was described in discovery.
3
Working Output
Getting the pipeline running end-to-end to produce a first result, then iterating for quality.
4
Eval & Demo
Formal evaluation against the test set, building the interface, and drafting the readout.

Foundation

02-01

Setup and Validation

Access & Environment Setup

  • Confirm model API credentials, read access, and representative test data.
  • This stage only ends when the FDE can run code against real data (or a reliable approximation).
  • Risk: Starting the build before access is confirmed creates rework.

Data Exploration

  • Examine the actual format. How consistent is the structure?
  • Does this sample reflect the real production population?
  • Warning: A pipeline designed without examining the actual data almost always requires significant rework.

Execution

02-01

Build and Evaluate

Building Toward Output

  • Goal: Take a real input, process it, and produce a result, even if quality is low.
  • Speed to first output matters more than getting to high quality quickly.
  • Once end-to-end, iterate against the agreed success metric on the test set, not personal judgment.

Eval & Async Updates

  • Send a brief async update daily: What was done, what is blocked, what happens next.
  • Sharing rough intermediate results keeps customers engaged.
  • Silence is dangerous: A customer who hears nothing fills the silence with concern.

Adaptability

02-01

When conditions don't match scoping

  • When access is delayed: Build with synthetic inputs or mock responses. Document exactly what is mocked and what real version will replace it.
  • When data differs: Build against what is actually available.
  • Report discrepancies precisely. "The data was harder than expected" is useless; state exactly how it differs and the build implications.
The formal evaluation must always run against real data, never against simulated inputs. The Integrity Rule

Every decision made because of missing data, delayed access, or an unexpected format should be documented at the moment it is made.

The Presentation

02-01

Running the POC Demo

The demo is a value narrative, not a technical feature tour. It has three distinct parts:

01   Before
Show the current state. How long does a typical case take today? This establishes the baseline for comparison.
02   During
Run the system on a typical real input. A typical input that produces a strong result is more persuasive than a cherry-picked perfect one.
03   After
Connect output to business impact. How much time was saved? What does that look like at weekly volume?

Measurement

02-01

Measuring and Deciding

Crucial Step: Confirm the Target

Before running the demo, confirm with the customer that the success metric from the scope document is still the agreed standard to prevent moving goalposts.

  • Primary Metric: "We agreed the target was X, and here is what we measured."
  • Latency: Does it meet the operational requirements?
  • Cost per Transaction: Is it within budget at projected production volume?
  • Edge Cases: Where does the system underperform, and how often?

Decision Point

02-01

The Three Possible Outcomes

All three are valid. The sprint succeeds when it produces a clear one.

Proceed
The metric was met, integration works, and customer is confident. Agree on next steps before leaving the room.
Pivot
The metric was not met, but the sprint revealed a specific path. Define what needs to change before the next attempt.
Stop
The approach doesn't work, or the cost/latency makes it infeasible. A stop outcome is the correct answer produced at the lowest possible cost.

Handoff

02-01

The Readout Document

The readout document officially closes the sprint. It is a single page covering:

  • What was built.
  • What was measured.
  • What the measurement showed.
  • The recommendation (Proceed, Pivot, Stop).
A Proceed decision does not mean the POC output moves directly to production. Managing Expectations

The POC answered one question: Does this approach work? The next phase builds a complete version to handle real inputs and real users.

The Sprint is Complete

Everything before the sprint was preparation. Everything after builds on what the sprint proved.
