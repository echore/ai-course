Pilot Phase, Handoff, & Feedback

Testing the system in real user environments, ensuring deployment readiness, and converting field observations into product intelligence.

Module 02-02  ·  End-to-End Delivery

The Transition

02-02

POC vs. The Pilot Phase

The POC sprint answered one question: Does the approach work?

The pilot answers a completely different question: Does a more complete version of the system work for its end users, in their day-to-day workflows, under operational conditions?

A system that hits 91% accuracy on a test set can still fail if users do not trust it or if the workflow integration creates friction.

A test set reveals technical performance under controlled conditions. Real users reveal organizational fit and unexpected input patterns. The Value of the Pilot

Scope Boundaries

02-02

What the Pilot Adds (and Excludes)

What is Included

  • Broader input coverage: The messy cases absent from the curated POC test set.
  • Live system integrations: Real auth, live feeds, and write-backs to user systems.
  • Error handling: Edge case logic is now addressed with operational depth.

Explicitly Excluded

  • Production-grade monitoring infrastructure.
  • Complete compliance and audit documentation.
  • Organization-wide scaling work.

These are explicit exclusions to keep the pilot contained, not deferred tasks.

The Agreement

02-02

The Pilot Scope & Shadow Mode

The scope creates a shared standard for "done" and helps the FDE manage scope expansion mid-flight.

Scope Elements
Must define: Capabilities, Integrations, specific Users, Timeline, and Success Criteria (performance, adoption, trust).
Feedback Cadence
Establish a weekly or bi-weekly rhythm of user check-ins. A pilot with no structured check-ins produces feedback too late to act on.
Shadow Mode (Optional)
The AI processes live requests, but outputs are hidden from users. FDEs compare accuracy against the manual process before going live.

Human Factors

02-02

Working with Real Users

1
Set Expectations
Tell them what the system does and doesn't do. Users without clear expectations will either over-rely on it or dismiss it after one error.
2
Capture Feedback
Set up a simple channel (Slack/Form) to capture the input, the output, and what was wrong. Vague feedback is not actionable.
3
Iterate in Scope
Address legitimate bugs, but log and defer new feature requests. Expanding scope mid-pilot distorts the evaluation.

Success Signals

02-02

Evaluating Pilot Performance

Metric performance is only one part of the evaluation. Three signals determine readiness:

Reliability
Stable latency and predictable output. Average metrics can look strong while hiding concentrated failure patterns in specific input categories.
Adoption
Do users organize their work around the system's output? Low adoption with strong metrics usually points to a usability issue.
Trust
Do users act on the output, or do they re-verify everything independently? High re-verification signals a lack of confidence.

Decision Point

02-02

Closing the Pilot

The pilot closes with a structured readout covering operational behavior, adoption data, trust signals, and a recommendation.

  • Proceed: All three signals are positive. Define deployment prerequisites.
  • Extend: One or more signals need intervention. Agree on a timeline.
Deployment Prerequisites: Required before FDE exit

Before handoff, the customer must commit to a named system owner, a support channel, and a monitoring plan.

Criteria

02-02

What "Deployment-Ready" Means

AI systems cannot be validated via standard tests alone because outputs are probabilistic.

Reliability
Processes requests consistently without silent errors.
Output Quality
Accuracy holds consistently at real deployment volume.
Safety
No output causes downstream harm without human review.
Cost
Token costs at volume are within committed budget.
Observability
The team can catch quality degradation early.

Deliverables

02-02

What the FDE Hands Off

1. Maintainable Code

  • Separates config from logic and avoids local dependencies.
  • Committed to a repo the customer team can access from day one.

2. The Live Session

  • An end-to-end walkthrough of architecture and monitoring.
  • Recorded so the team can refer back to it.

3. The Handoff Document

  • System Overview: What it does and doesn't handle.
  • Data Flow: Where data moves and what hits external APIs.
  • Failure Modes: How it fails and what triggers it.
  • Monitoring Setup: What each alert means operationally.
  • Escalation Path: When a human should intervene.

Operations

02-02

Monitoring a Deployed AI System

Quality can degrade gradually without any technical errors appearing in logs.

  • Latency & Error Rate: Is performance stable under load?
  • Output Quality Sampling: Take a random sample weekly to catch drift before it becomes a user complaint.
  • Cost per Query: Spikes can indicate agentic loops.
  • User Engagement: A rising override rate signals quality drift.
Human-in-the-Loop Fallback Configured mechanisms

Must define a Trigger (e.g., low confidence score), a Queue (who reviews it), and Logging (to capture overrides for future evals).

Infrastructure

02-02

Logging and The Clean Exit

Structured Data Handling

  • Use consistent JSON objects for logging to query at scale.
  • Do not store full PII or customer-identifying data in general-purpose logs. Access it via primary storage when needed.

The Post-Handoff Relationship

  • Internal Champion: Must handle routine questions and onboarding.
  • Support Window: Define how long the FDE is available and what is in-scope. An undefined window creates an indefinite dependency.

Product Intelligence

02-02

The Field Feedback Loop

FDEs are technically deep and organizationally close enough to see how the product performs in real use.

Building the Habit
Capture product gaps, integration friction, documentation gaps, and customer workarounds in real-time.
Signal vs. Noise
A customer's unusual data structure is noise. The absence of a standard connector across multiple clients is a signal.
The Time Dimension
Some signals only become visible after the second or third time the FDE encounters them across different projects.

Communication

02-02

Writing Useful Product Feedback

The 6 Elements of Feedback

  • Problem observed: What the customer encountered.
  • Frequency: How often it occurred.
  • Severity: Did they build a workaround?
  • What they tried: Reveals their expectations.
  • What solves it: A concrete fix from the user perspective.
  • Estimated impact: Business value of the fix.

Working with Internal Teams

  • The FDE is a signal source, not the product team's customer. Feedback is an input, not an instruction.
  • Escalations: Provide clear reproduction steps and business impact. Urgent requests with no context get deprioritized.

Compounding Value

The feedback loop is how fieldwork compounds. Each project delivers value to the customer and intelligence that makes the product stronger.
