Why this matters

02-02

Architecture changes the delivery work

The system type you recommend during scoping shapes the build, evaluation, and customer handoff.

Build & scope

  • A fixed workflow has known stages and defined interfaces.
  • An agent adds decisions, tool coordination, and variable execution paths.

Evaluation

  • A workflow needs output and stage-level checks.
  • An agent also needs checks on actions, recovery, and task completion.

Customer ownership

  • The team must diagnose failures and maintain integrations.
  • Greater autonomy requires clearer operating limits and escalation.
Choose the architecture around the customer’s workflow and constraints.

The core distinction

02-02

Two categories, one runtime question

Runtime means what happens while the system processes a real request.

LLM-based non-agentic system

Application code defines the sequence of operations. The model completes a task within that prescribed path.

  • May include retrieval, validation, and multiple model calls.
  • Does not independently change its approach after observing results.

Agentic system

The model selects a next action, receives the result, and uses it to decide what to do next.

  • The path and number of steps can vary by request.
  • Operates within permissions and limits enforced by the application.
Ask who chooses the next step—not how many tools or model calls exist.

Non-agentic systems

02-02

A fixed workflow turns input into a defined output

Example: read a contract and return a structured clause summary.

Prepare input

Extract the text and supply the relevant instructions.

→

Run the LLM

Identify clauses and populate a defined output structure.

→

Validate & return

Check required fields and route incomplete results for review.

What stays fixed

The application always follows prepare → extract → validate. Exceptions use predefined handling.

What can vary

Different contracts produce different summaries. Model errors are still possible even when the processing path is fixed.

A predictable processing path helps you locate where an error entered the system.

Where fixed workflows help

02-02

Common enterprise tasks fit this pattern

Many customer problems require a well-defined transformation rather than open-ended investigation.

Classification & extraction

  • Route customer emails to a queue.
  • Extract dates, entities, and clauses into a schema.

Summarization & generation

  • Condense a document into an agreed summary format.
  • Draft content from a defined set of inputs.

Structured question answering

  • Retrieve relevant knowledge and generate an answer.
  • Return evidence or route unanswered questions to a person.
For the FDE: define representative inputs, acceptable outputs, and the failure-handling path.

A useful boundary case

02-02

Retrieval can still follow a fixed path

Retrieval-augmented generation, or RAG, supplies external information to the model before it answers.

Retrieve

Fetch relevant documents from the knowledge source.

→

Generate

Use the retrieved context to produce an answer.

→

Check

Validate the format and supporting evidence.

Predefined RAG workflow

The application runs the same stages for each question. A retrieval step alone does not make it agentic.

Adaptive retrieval

The model may judge that evidence is incomplete, choose another search, and change its approach based on the result.

The architectural boundary is adaptive control over the process.

Agentic systems

02-02

An agent selects actions from new evidence

An agent receives a goal and works through a repeated decision–action–observation loop.

Decide

Select an action using the goal and current context.

→

Act

The application executes an allowed tool request.

→

Observe

Return the tool result and update the session context.

→

Continue or stop

Choose another step, finish, or request help.

A variable execution path

A result can change the next useful action. Some requests finish quickly; others need additional investigation.

A bounded loop

Define completion, step or time limits, and when the system must hand control to a person.

The model proposes actions; the surrounding application controls execution.

Worked example

02-02

One support workflow makes the difference concrete

Task A · Route an email

Input: “My order has not arrived.”

  • Classify the request as a delivery issue.
  • Return the delivery-support queue.
  • The output is a label; the processing sequence is predefined.

Task B · Investigate the delivery

Goal: establish what happened and recommend a next step.

  • Look up the order and inspect carrier tracking.
  • An address error may trigger an address check; a carrier delay may trigger a different inquiry.
  • Return a supported recommendation or escalate unresolved cases.
The investigation may benefit from an agent when the next useful step depends on what the system discovers.

Architecture recap

02-02

The distinction is about behavior at runtime

Recognize a fixed workflow

Code prescribes the path. Retrieval, validation, and several LLM calls can all fit inside it.

Recognize an agent

The model uses observations to select subsequent actions. The path varies within application controls.

Connect to FDE work

Adaptive behavior changes the evaluation surface and the responsibilities passed to the customer.

With the architectures defined, we can now connect model capability to scoping and evaluation.

Model capability

02-02

Reasoning and autonomy are separate choices

Reasoning is the ability to work through a problem. Autonomy is the system’s authority to choose and take actions.

Reasoning inside a fixed workflow

A model can analyze a difficult contract, compare clauses, and explain an inconsistency while the application still prescribes every processing stage.

  • Evaluate task accuracy and the usefulness of the result.
  • Measure latency and cost on representative customer inputs.

Autonomy inside an agent

The model may choose which tool to call next. The application determines which tools and actions are permitted.

  • Evaluate action selection as well as the final output.
  • Define limits and escalation independently of model capability.
A stronger reasoning model does not, by itself, make the system agentic.

System architecture

02-02

The harness manages the execution loop

The harness is the surrounding software that connects the model to context, tools, controls, and execution records.

Context & tool interfaces

  • Supply the goal, relevant records, and previous observations.
  • Define tool inputs, outputs, and errors clearly.

Execution controls

  • Enforce access permissions and approval boundaries.
  • Limit steps, elapsed time, and resource use.

Visibility & recovery

  • Record tool requests, results, and status changes.
  • Handle failures, retries, and escalation.
A tool request is a proposal to execute—not proof that the action succeeded.

Operational tradeoffs

02-02

Adaptive execution adds failure modes

The additional flexibility can be useful, but every tool interaction creates another place to fail.

A wrong next action

The model chooses an irrelevant search or interprets a tool result incorrectly.

Check tool selection and whether the conclusion is supported by observations.

A failed or repeated action

A service times out, or a retry risks repeating a write that already succeeded.

Define failure handling and ways to prevent duplicate changes.

An unfinished investigation

The system keeps searching without a useful outcome, increasing latency and cost.

Set a budget and route unresolved work to an owner.

For customer-changing actions, specify what can run automatically and what needs approval.

FDE scoping

02-02

Scope the behavior before you build

Turn the customer’s request into a concrete outcome, a runtime path, and defined boundaries.

Outcome & inputs

  • What observable customer result counts as success?
  • Which records and representative cases are available?
  • What remains outside the scope?

Runtime & actions

  • Can a fixed workflow cover the required cases?
  • If adaptive steps help, which tools may it use?
  • Which changes require review, and when must it stop?

Operations & owner

  • What time and cost budgets apply?
  • Who receives failures and unresolved cases?
  • What evidence will justify expanding the pilot?
Example outcome: produce a supported delivery explanation; escalate when the evidence is incomplete.

Customer ownership

02-02

Hand off a system the customer can operate

Fixed workflow handoff

  • Input and output contracts; pipeline configuration.
  • Prompts, validation rules, and known failure cases.
  • Evaluation examples and an owner for updates.

Agentic system handoff

  • All workflow essentials, plus tool access and permission boundaries.
  • Execution records, limits, and approval configuration.
  • A runbook for failed actions, unfinished tasks, and escalation.
The customer should be able to explain a failure, identify its owner, and decide the next action.

Scoping exercise

02-02

Apply the decision to a new customer request

Choose a starting architecture, then state how you would evaluate it.

A · Extract renewal dates

Read a batch of contracts and return renewal dates with supporting text.

  • Start with a fixed extraction and validation workflow.
  • Check dates, evidence, missing clauses, and ambiguous language.

B · Investigate invoice mismatches

Compare customer records and choose further checks based on discrepancies.

  • Consider an agent when the investigation path varies.
  • Check evidence, tool decisions, permitted actions, and escalation.
If B can be covered by a reliable predefined procedure, test that simpler approach first.

Choose the architecture the customer can own

Match runtime behavior to the problem. Evaluate the full system. Make ownership explicit.
