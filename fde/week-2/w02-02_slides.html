The architectural distinction

02-02

Who decides the next step?

Classify the system by how it operates at runtime.

Non-agentic workflow

Application code defines the processing path.

Agentic system

The model selects the next action using results from earlier steps.

Model capability and system autonomy are separate decisions.

LLM-based non-agentic systems

02-02

A fixed path can solve valuable problems

Input

A contract or customer email

→

LLM

Extract, summarize, or classify

→

Output

Structured summary or queue label

Common tasks

Clause extraction · summarization · support routing

FDE advantage

A fixed path does not guarantee identical model outputs.

A useful boundary case

02-02

Retrieval does not automatically mean agentic

Retrieve

Fetch relevant documents

→

Generate

Answer using retrieved context

→

Validate

Check format and evidence

Several steps can still form a predefined workflow.

Ask: Does the model choose whether to search again or change its approach?

Agentic systems

02-02

An agent works through a feedback loop

Decide

Choose the next action

→

Act

Request a tool call

→

Observe

Read the tool result

→

Repeat or stop

Continue toward the goal

The application executes allowed actions; the model proposes them.

Stop on completion, a budget limit, a blocked task, or a required human decision.

Support example

02-02

Same customer, different architecture

Route this email

Email → category → queue

A predefined workflow is usually enough.

Investigate a failed delivery

Check order → inspect tracking → choose a follow-up

An agent may help when the next step depends on what it finds.

A refund or account change can require approval before execution.

Model choice

02-02

Reasoning ability is not autonomy

Reasoning

The model’s ability to work through a difficult problem.

Autonomy

The system’s permission to select and take actions.

A reasoning model can sit inside a fixed extraction pipeline.

Evaluate the model on the actual task; evaluate the system on its behavior.

System engineering

02-02

The harness makes the loop operable

The harness is the surrounding software that manages execution.

Context & tools

Provide relevant state and well-defined tool interfaces.

Control

Enforce permissions, approvals, timeouts, and step limits.

Visibility & recovery

Log execution, handle tool failures, and support escalation.

A stronger model does not replace these system responsibilities.

Scoping checklist

02-02

Start with the simplest sufficient system

01 · Define success

What observable outcome must the customer get?

02 · Test a fixed path

Can a predefined workflow reliably deliver it?

03 · Bound autonomy

If adaptive steps help, define tools, limits, and ownership.

Add autonomy when measured customer value justifies the added complexity.
